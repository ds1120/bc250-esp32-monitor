# OTA 전송 중단 처리 — 5.8.4

5.8.3에서 5.8.4 수정본을 보내던 첫 시도는 PC 업로더의 45초 전송 제한으로 실패했습니다. 사용자는 업데이트 화면이 남아 있다고 보고했고, PC를 정상 종료한 뒤 ESP32를 재시작해 5.8.3으로 복구했습니다. 이후 전송에서 TCP 확인 응답을 관찰한 결과 1.26MB 이미지가 45초보다 오래 걸리는 느린 전송임을 확인했습니다. 전송 속도 저하의 근본 원인은 아직 판정하지 않았습니다.

Arduino-ESP32 2.0.17의 WebServer 원본 `_uploadReadByte`는 연결이 유지된 채 데이터가 오지 않으면 무기한 대기할 수 있습니다. 5.8.4는 원 저작권·LGPL 라이선스와 전체 WebServer 소스를 보존한 로컬 라이브러리를 사용하고, 10초 동안 추가 데이터가 없으면 해당 HTTP 클라이언트만 닫고 업로드 중단 경로로 복귀하도록 수정했습니다. ESP32 리셋이나 릴레이 OFF를 수행하지 않습니다. 해당 생산 코드 메서드를 직접 컴파일하는 테스트로 즉시/지연 수신, 무수신, 연결 종료, 타이머 wraparound를 검사합니다.

PC 업로더의 전송 소켓 제한은 기본 120초이며 `--upload-timeout 10..300`으로 조절합니다. 이 값은 전송이 진행되는 느린 연결을 위한 PC 쪽 제한이며, 펌웨어의 10초 **무수신** 제한과 다릅니다. 10초 동안 바이트가 계속 도착하면 전체 전송이 10초보다 오래 걸려도 정상 진행합니다.

릴레이 유지 OTA의 RTC ABI는 기존 `BC250-RELAY-HOLD1@50000200`을 유지합니다. EN/리셋 버튼, 전원 상실, USB 업로더 리셋에는 같은 보장이 없습니다. 업데이트 중 원격 응답이 없다고 ESP32 리셋을 누르지 않습니다. 필요하면 PC를 먼저 정상 종료하고 ESP32를 재시작합니다.

5.8.4는 OTA가 시작되면 Wi-Fi 절전 모드를 일시 해제하고, 업로드 취소/실패 시 이전 모드로 복구합니다. 정상 완료 후에는 기존 릴레이 유지 재시작 절차를 따릅니다. 불안정한 링크를 위한 PC 업로더의 `--tcp-mss 536` 선택지도 추가했으며 기본값도 536으로 사용합니다. `--tcp-mss 0`은 운영체제 기본값을 사용합니다. 작은 분할에서도 HTTP 데이터가 바뀌지 않는 것은 로컬 전송 테스트로 확인합니다.

이번 적용에서는 큰 TCP 세그먼트 전송이 반복적으로 지연됐으나, `--tcp-mss 536`으로 5.8.4 전체 전송과 재부팅 확인에 성공했습니다. PC 부팅 ID 유지, 릴레이 HIGH 복귀, SD 설정 보존을 확인했습니다. 현재 이미지의 실제 중단 시험은 수행하지 않았으며, 10초 무수신 처리는 생산 메서드 컴파일 테스트로 확인했습니다.
